**Android-приложение**

Основные файлы: \ 

1. Service.kt - основной фоновый сервис, реализующий сбор и от-
правку данных;
2. LocationActivity.kt - активность для отображения координат
в реальном времени;
3. TelephonyActivity.kt - активность для просмотра сырых дан-
ных о сети;
4. ServiceActivity.kt - интерфейс управления запуском/останов-
кой сервиса;
5. AndroidManifest.xml - декларация компонентов, разрешений и
метаданных приложения.

---

Для получения координат используется LocationManager - систем-
ный сервис, предоставляющий доступ к провайдерам местоположения (GPS,
Network, Passive). В проекте настроен запрос обновлений с параметрами: \ 
1. Провайдер: LocationManager.GPS_PROVIDER (наибольшая
точность);
2. Интервал: 5000 мс (5 секунд);
3. Минимальное смещение: 1 метр.

---

Класс TelephonyManager предоставляет доступ к информации о се-
ти. Метод getAllCellInfo() возвращает список объектов CellInfo, ко-
торые могут быть одного из типов: \ 
1. CellInfoLte - параметры соты LTE (PCI, EARFCN, RSRP, RSRQ,
RSSI, RSSNR, TA, CQI, ASU);
2. CellInfoNr - параметры соты 5G NR (PCI, NCI, NR-ARFCN, SS-
RSRP, SS-RSRQ, SS-SINR);
3. CellInfoGsm - параметры соты GSM (Cell ID, ARFCN, BSIC, LAC,
уровень сигнала).

**Получение данных с телефона**

Реализуется с помощью установления TCP-соединения по сокетам. \ 
На стороне Android: \ 
1. Собранные данные (координаты, параметры сети) сериализуются в
JSON-объект.
2. Создаётся ZMQ.REQ-сокет и устанавливается соединение с сервером
по адресу tcp://<IP>:5555.
3. JSON-строка отправляется в виде байтового массива в кодировке
UTF-8.
4. Клиент ожидает ответ “ACK” в течение заданного таймаута (3000 мс).
14
5. При успешном получении подтверждения данные считаются достав-
ленными; при ошибке — сохраняются в локальный файл для повтор-
ной отправки.

---

На стороне сервера: \ 
1. Сервер создаёт ZMQ.REP-сокет и начинает прослушивание порта
5555 на всех интерфейсах.
2. При получении сообщения оно десериализуется из JSON в структуру
LocationData.
3. Данные обрабатываются: сохраняются в базу данных, обновляются в
оперативной памяти для GUI.
4. Сервер отправляет подтверждение “ACK” обратно клиенту

**База данных**

В качестве базы данных выступает реляционная PostgeSQL \

1. Подключение: Метод testConnection() проверяет доступность
базы данных, создавая тестовое соединение с параметрами из конфигурации.
2. Вставка данных: Метод insertLocationData() принимает объ-
ект LocationData и выполняет параметризованный INSERT-запрос в соот-
ветствующую таблицу (в зависимости от networkType). Используется кон-
струкция ON CONFLICT(time) DO NOTHING для предотвращения дубли-
рования записей с одинаковой временной меткой.
3. Выборка для визуализации: Функция fetchDBPoints() выполня-
ет запрос к объединённому представлению всех трёх таблиц, выбирая коорди-
наты последних g_maxDbPoints записей для отображения точек на карте.
4. Результаты сохраняются в глобальный вектор g_dbPoints с защитой мью-
тексом для потокобезопасного доступа из GUI.

**Тайлы OSM и их обработка**

Процесс загрузки тайла: \ 
1. Формируется локальный путь к файлу: tiles/<zoom>/<x>/<y>.png.
2. Если файл существует, он загружается напрямую.
3. Если файла нет, формируется URL OpenStreetMap и выполняется за-
прос через libcurl.
4. Полученные PNG-данные сохраняются в кэш на диске и в оператив-
ной памяти.

---

Преобразование PNG в OpenGL-текстуру: \ 
1. Библиотека stb_image декодирует PNG в сырой массив байтов
формата RGBA (4 байта на пиксель).
2. Создаётся идентификатор тектуры OpenGL через glGenTextures.
3. Текстуре назначаются параметры фильтрации (GL_LINEAR) для
плавного масштабирования.
4. Данные загружаются в видеопамять через glTexImage2D.
5. После загрузки сырой массив освобождается, остаётся только иденти-
фикатор текстуры.

**Тепловая карта**

Используется метод IDW. \ 

Значение в точке вычисляется как взвешенное среднее значений бли-
жайших измерений; \ 
1. Вес каждого измерения обратно пропорционален расстоянию до него
в степени P (в проекте P=1.0 для плавности);
2. Если расстояние меньше 0.5 метра, используется точное значение без
интерполяции.

---

Оптимизации вычислений: \ 
1. Предварительная фильтрация: отбираются только точки в радиусе
R от текущего тайла;
2. Адаптивный радиус: R масштабируется с зумом: R_zoom = R_-
base · 2^(14-zoom);
3. Кэширование результатов: сгенерированные тайлы тепловой карты
сохраняются в папку heatmap/ с учётом параметров (критерий, ра-
диус, фильтры EARFCN/PCI).
4. Раскраска: Значения параметра отображаются через линейный гради-
ент из 8 цветов, от фиолетового до красного.
